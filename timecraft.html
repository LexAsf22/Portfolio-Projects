Database Migration with Flyway

Very Important
✓ Flyway is recommended over Liquibase for this project. It uses plain SQL files (no XML/YAML), is simpler to set up with Spring Boot, and is easier for beginners to understand and debug.

Why database migration is important

  • Version control for your database — every schema change is tracked like a Git commit
  • Team collaboration — everyone on the team gets the same DB structure automatically
  • Safe deployments — migrations run automatically when the app starts, no manual SQL scripts
  • Rollback tracking — you know exactly what changed and when, making debugging easier
  • Production safety — no more "forgot to run the SQL on the server" issues
1
App starts up
Spring Boot launches and Flyway activates automatically
2
Flyway checks DB
Reads the flyway_schema_history table to see what's already been run
3
Runs new scripts
Executes any V*.sql files not yet applied, in version order
4
App is ready
DB schema is now up to date. App continues loading normally

Migration file naming convention

Files go in: src/main/resources/db/migration/

File nameWhat it does
V1__create_users_table.sqlCreates the users table with roles, email, password hash
V2__create_departments_table.sqlCreates the departments table
V3__create_rooms_table.sqlCreates the rooms table with capacity and type
V4__create_subjects_table.sqlCreates the subjects table with units and department FK
V5__create_teachers_table.sqlCreates the teachers table linking to users
V6__create_teacher_availability.sqlStores teacher day/time preferences
V7__create_schedules_table.sqlCreates the main schedules table with all FKs
V8__seed_initial_data.sqlInserts default admin user and sample departments
⚠ Never edit an existing migration file after it has been run. Flyway checksums each file — if you change a file that's already been applied, the app will refuse to start. Always create a new V9__... file for changes.

React → Spring Boot

  • All calls go through services/api.js (Axios instance)
  • JWT token attached to every request header automatically
  • Base URL stored in .env as VITE_API_BASE_URL
  • Axios interceptors handle token expiry and redirect to login

Spring Boot → PostgreSQL

  • Repositories extend JpaRepository — no SQL needed for basic CRUD
  • Custom queries use @Query with JPQL for complex joins
  • Flyway handles schema at startup — DB is always in sync
  • Connection pooling via HikariCP (built into Spring Boot)

Database Design

TableKey FieldsRelationships
users id, email, password_hash, role (ADMIN/TEACHER/STUDENT), is_active, created_at One user → one teacher profile OR one student profile
departments id, name, code, head_teacher_id One department → many subjects, many teachers, many students
rooms id, room_code, name, capacity, type (LAB/LECTURE/SEMINAR), building One room → many schedule slots (but not at the same time — conflict check)
subjects id, code, name, units, hours_per_week, department_id, year_level Belongs to one department · assigned to teachers via schedules
teachers id, user_id (FK), employee_id, department_id, max_hours_per_week One teacher → many availability slots · many schedule assignments
teacher_availability id, teacher_id, day_of_week, start_time, end_time, is_preferred Many availability rows per teacher — used as input to scheduling engine
schedules id, subject_id, teacher_id, room_id, section, day_of_week, start_time, end_time, semester, academic_year, status Central table — references subjects, teachers, rooms. Conflict detection runs against this table.

Key Relationships at a Glance

  • Department → Subjects: One department has many subjects (1:N)
  • Department → Teachers: One department has many teachers (1:N)
  • Teacher → Availability: One teacher has many time slots (1:N)
  • Schedule: Joins teacher + subject + room + time slot — the core conflict table (N:1 to each)
  • Conflict rule: No teacher, room, or subject section can appear twice at the same day+time

Feature-Based Module Design

Module 1

Authentication & Users

Handles login, registration, JWT issuance, role-based access. Three roles: ADMIN, TEACHER, STUDENT. Spring Security + JWT.

  • Controller AuthController
  • Service AuthService, UserDetailsServiceImpl
  • Security JwtUtil, JwtAuthFilter
  • Endpoints POST /auth/login, /auth/register
Module 2

Scheduling Engine

The core of TimeCraft. Accepts constraints (rooms, teacher availability, subjects) and generates a conflict-free timetable.

  • Service ScheduleService, ConflictDetectionService
  • Logic Greedy assignment + backtracking
  • Endpoints POST /schedules/generate, GET /schedules
Module 3

Subject & Teacher Management

Admin manages subjects and departments. Teachers set their availability and subject preferences.

  • Controllers SubjectController, TeacherController
  • Endpoints CRUD for /subjects, /teachers, /departments
  • Feature Teacher availability calendar input
Module 4

Reporting

Generates teaching load reports, room usage summaries, and department schedule overviews. Exportable as PDF/CSV.

  • Controller ReportController
  • Service ReportService
  • Endpoints GET /reports/teaching-load, /reports/room-usage

Scheduling Logic

How timetable generation works (conceptual)

The scheduling engine lives in ScheduleService.java and is called when Admin triggers "Generate Schedule." It works in three phases:

Phase 1 — Collect inputs

  • All subjects for the semester
  • Teacher availability slots
  • Room list with capacity + type
  • Existing schedule constraints (holidays, fixed slots)

Phase 2 — Assign slots

  • For each subject, find an available teacher
  • Check teacher is free at the time slot
  • Find a room that is free + has enough capacity
  • If conflict found → try next slot (backtrack)

Phase 3 — Conflict check

  • Teacher double-booked at same time?
  • Room double-booked at same time?
  • Section assigned two subjects at same time?
  • Teacher hours exceed max_hours_per_week?
Scheduling Algorithm Flow
  Input: subjects[], teachers[], rooms[], availabilities[]

  FOR each subject in subjects:
    FOR each available time_slot:
      teacher = findAvailableTeacher(subject, time_slot)
      room    = findAvailableRoom(subject.capacity, time_slot)

      IF teacher != null AND room != null:
        IF !hasConflict(teacher, room, section, time_slot):
          assign(subject, teacher, room, time_slot)  ← success
          BREAK
        ELSE:
          log conflict, try next slot  ← backtrack

  IF subject still unassigned after all slots tried:
    → throw ScheduleConflictException (notify admin)

  Output: List of Schedule entries saved to DB
ℹ Algorithm recommendation: Start with a Greedy algorithm (assign first available slot). If too many conflicts arise in testing, upgrade to a Constraint Satisfaction Problem (CSP) solver or use a library like OptaPlanner (by Red Hat, works with Spring Boot natively).

Frontend Structure (React JSX)

Routing Strategy

Use React Router v6 with role-based protected routes. The ProtectedRoute.jsx component checks the user's role from AuthContext and redirects if unauthorized.

  • /login — public
  • /admin/* — ADMIN role only
  • /teacher/* — TEACHER role only
  • /student/* — STUDENT role only

API Services Pattern

All API calls are in services/. Components never call Axios directly — they call service functions. This makes it easy to swap the API URL or add mock data during testing.

  • api.js — base Axios instance
  • JWT automatically attached via interceptor
  • 401 responses auto-logout via interceptor

Suggestions & Best Practices

🔒 Security

  • Never store plain passwords — Spring Security's BCryptPasswordEncoder handles hashing
  • Use short JWT expiry — 15 min access token + 7 day refresh token
  • Role-based method security — use @PreAuthorize("hasRole('ADMIN')") on service methods
  • Never put DB credentials in code — use application.yml with env variable references
  • CORS config — explicitly whitelist only http://localhost:3000 in dev, your domain in prod

📐 Clean Architecture

  • Controller → Service → Repository — never skip layers, never call repository from controller
  • Always use DTOs — never expose entity objects directly in API responses
  • One service per domain — ScheduleService only does scheduling, not user management
  • Global exception handler — use @ControllerAdvice to return consistent JSON errors

📦 Scalability

  • Add pagination — all list endpoints should use Pageable from Spring Data
  • Cache schedule reads — use Spring Cache + Redis for timetable queries (read-heavy)
  • Async generation — run schedule generation in a background thread (@Async) for large datasets
  • Index FK columns — add DB indexes on teacher_id, room_id, day_of_week in schedules table

🔮 Future Improvements

  • OptaPlanner — replace greedy algorithm with a proper CSP solver for better schedules
  • WebSocket / SSE — push schedule updates to students/teachers in real-time
  • Email notifications — use Spring Mail when schedule is published or changed
  • PDF export — generate printable timetables using iText or JasperReports
  • Docker — containerize Spring Boot + React + PostgreSQL together
