Project Analysis

From the uploaded project structure, Spacio is a facility/lab reservation management system with three user roles (Admin, Teacher, Student). It follows a flat PHP MVC-like structure with no formal framework.

🔐 Authentication

Session-based PHP auth via auth.php. No JWT or token system currently in place. Login/logout handled in root login.php and logout.php.

🗄️ Database Layer

Centralized in database.php. Likely uses PDO or MySQLi. No ORM — raw SQL queries throughout. Single database shared by all roles.

🗂️ Routing

No framework router. Navigation relies on direct PHP file references. Role-based access enforced manually per file using session checks.

🧩 API Layer

Minimal — only check_availability.php exists as an API endpoint. No REST architecture, no versioning, no standard response format.

02

Suggestions

Very Important
⚠ These are practical improvements to make before or during Django integration. Skipping these will make the migration harder later.

🔧 What to Improve in the Current PHP Project

  • No input sanitization layer — each PHP file likely handles user input differently. Centralize this in helpers.php before integration.
  • No error handling standard — add a consistent JSON error response format so Django APIs can understand PHP's failures.
  • Session security is unclear — enforce session_regenerate_id() on login and set secure cookie flags in auth.php.
  • No API versioning — add a version prefix now (e.g. /api/v1/) to avoid breaking changes when Django takes over endpoints.
  • Direct DB calls everywhere — consider wrapping all DB calls inside model-like functions in helpers.php for easier migration.
  • Missing .env file — DB credentials and secrets should be in a .env file, not hardcoded in database.php.

✅ Keep in PHP

  • All frontend views (admin, student, teacher dashboards)
  • Session-based login/logout pages initially
  • Static assets (CSS, JS, images)
  • PHP includes (header, footer, flash messages)
  • index.php as application entry point

→ Move to Django

  • check_availability.php → Django REST API
  • Reservation logic and conflict detection
  • Reports and analytics generation
  • Email/notification services
  • Authentication (eventually — JWT tokens)
  • Background tasks (maintenance schedules)

📈 Performance, Scalability & Security Improvements

  • Add Redis caching — use Django's cache framework + Redis to cache availability checks and dashboard data
  • Rate limiting on APIs — Django REST Framework (DRF) supports throttling; PHP has none currently
  • Use PostgreSQL over MySQL — better Django ORM support, JSON fields, and concurrent reservation handling
  • Add CSRF protection — PHP has it via forms; Django enforces it automatically via middleware
  • Centralize logging — Django's logging framework + a tool like Sentry for both PHP and Python errors
  • Containerize with Docker — run PHP (Nginx/Apache) and Django (Gunicorn) as separate services

Integration Strategies

Option 1 · Recommended for Spacio

Django as a REST API Microservice

PHP frontend continues to handle all views and user sessions. A new Django project runs as an independent API server. PHP calls Django via cURL/HTTP for specific operations (availability, reports, reservations). Both systems share the same database.

Pros

  • Zero disruption to PHP frontend
  • Django APIs can be built incrementally
  • Clear separation of concerns
  • Easy to test in isolation
  • PHP team keeps working normally

Cons

  • Two servers to run and maintain
  • cURL adds latency vs direct DB calls
  • Auth coordination required
  • Slightly more complex deployment
Option 2 · Long-Term Goal

Gradual Migration from PHP to Django

Over several months, PHP pages are progressively replaced by Django views using Django Templates or a React/Vue SPA. The PHP system handles traffic until each module is fully migrated and tested. A reverse proxy (Nginx) routes requests to either PHP or Django based on URL prefixes.

Pros

  • End goal: full Django system
  • Each piece tested before cutover
  • No big-bang rewrite risk
  • Team learns Django gradually

Cons

  • Long transition period (6–18 months)
  • Two codebases to maintain during migration
  • Risk of feature drift between old/new
  • Auth sync is complex mid-migration
Option 3 · Simplest Start

Hybrid System — Nginx Reverse Proxy

Nginx acts as a smart gateway. Requests to /api/* are forwarded to Django (port 8000). All other requests go to PHP (Apache/port 80). Both share the database. No cURL needed — Nginx handles the routing transparently.

Pros

  • No PHP code changes needed
  • Clean URL-based separation
  • Nginx handles load balancing
  • Easy to add Django routes over time

Cons

  • Nginx configuration complexity
  • Session/auth sharing still needed
  • Harder to debug routing issues
  • Requires server-level access
✓ Our recommendation for Spacio: Start with Option 1 (Django as REST API). It's the safest, most practical path. Once the team is comfortable with Django and the APIs are proven stable, gradually migrate toward Option 2 for full replacement.

Database Design

✅ Shared Database (Recommended for Spacio)

Both PHP and Django connect to the same MySQL/PostgreSQL database. Django uses its ORM to map to existing tables. No data sync needed.

  • No data duplication
  • Reservations visible instantly to both systems
  • Single source of truth
  • Easier for a small team to manage
  • Django migrations must preserve existing PHP table structure
  • Use managed = False initially in Django models
VS

Separate Databases

PHP keeps its existing database. Django gets a new database for new features only. Data is synced via API calls or a message queue.

  • Complete isolation between systems
  • Can migrate DB schema independently
  • Complex data synchronization required
  • Risk of data inconsistency
  • Much more overhead for a small project
  • Not practical for Spacio at this stage

📋 Suggested Core Tables

TableKey FieldsUsed By
usersid, name, email, password_hash, role, created_atPHPDjango
labsid, name, capacity, type, status, imagePHPDjango
equipmentid, name, lab_id, quantity, statusPHPDjango
reservationsid, user_id, lab_id, start_time, end_time, status, approved_byDjango
issuesid, reported_by, lab_id, description, status, created_atDjango
maintenanceid, lab_id, scheduled_at, performed_by, notesDjango

⚙️ Django DB Configuration Note

In settings/base.py, point Django to the same database as PHP. Use managed = False in Django models for existing PHP-owned tables (users, labs, equipment) to prevent Django from overwriting them with migrations. Only tables that Django "owns" (reservations, issues) should have managed = True.

Authentication Strategy

🐘 Keep Auth in PHP

PHP continues to handle all login/logout and session management. Django APIs verify a shared secret API key — no user-level auth in Django.

  • Simplest to implement
  • No changes to existing auth
  • Can't do per-user auth in Django
  • Not scalable long-term

🔑 JWT Token Sharing

PHP handles login form and session. On successful login, PHP calls Django to get a JWT. JWT is stored in session and passed on every API call.

  • Best of both worlds
  • Django can verify user identity
  • Stateless — scalable API
  • Minimal PHP changes
  • Requires token refresh logic

🌐 Full Auth in Django

All login/logout moved to Django. PHP calls Django auth API to validate every request. PHP sessions replaced with JWT stored in cookies.

  • Clean long-term architecture
  • Django controls all security
  • Large PHP refactor needed
  • High risk of breaking sessions
  • Not for Phase 1
✓
Recommended: JWT Token Sharing
Phase 1: Keep PHP sessions + add API key auth on Django endpoints.
Phase 2: Introduce JWT — PHP gets a token on login, stores in session, sends on every API call.
Phase 3 (optional): Move full auth to Django and replace PHP sessions with JWT cookies.
Phase 1 — API Key Auth Flow ASCII 
  PHP Login     →  validate credentials (against DB directly)
                →  set PHP session: $_SESSION['user_id'], $_SESSION['role']
                →  all PHP pages use PHP session as before

  PHP API call  →  curl to Django /api/v1/availability/
                →  adds header:  X-API-Key: YOUR_SHARED_SECRET_KEY
                →  Django middleware checks X-API-Key header
                →  if valid → process request → return JSON
                →  PHP parses JSON → renders in view

Step-by-Step Migration Plan

⚠ Always test each phase fully in a staging environment before deploying to production. Keep PHP system fully functional at all times during migration.
1

Preparation Week 1–2

Audit existing PHP code. Add .env file for DB credentials. Create a staging copy of the database. Add API response helper to helpers.php. Set up Git branching strategy (main/staging/feature).

2

Django Project Setup Week 2–3

Install Python, create virtual environment, install Django + DRF + djangorestframework-simplejwt. Connect Django to the existing database using managed = False models. Verify Django can read existing data without touching it.

3

Migrate First API: Availability Check Week 3–4

Replace check_availability.php with a Django endpoint at /api/v1/availability/. Create django_bridge.php in PHP to call Django via cURL. Update PHP frontend pages to use the bridge instead of the old PHP file. Run both in parallel, compare outputs, then switch over.

4

Add JWT Authentication Week 5–6

Add Django JWT auth endpoint. Modify login.php to call Django login API and store JWT in PHP session alongside existing session. Update django_bridge.php to send JWT in Authorization header. Test all three user roles (admin, student, teacher).

5

Migrate Reservation Logic Week 7–9

Move reservation creation, approval, and cancellation to Django APIs. Update PHP reservation pages (reserve_lab.php, reserve_equipment.php, my_reservations.php) to call Django APIs. Keep PHP as the view layer — Django handles all data mutations.

6

Migrate Reports & Issues Week 10–12

Move reports.php and report_issue.php logic to Django analytics endpoints. Django can use aggregation queries, caching, and background tasks (Celery) for heavy reports. PHP renders the results in existing templates.

7

Production Deployment Week 13+

Set up Nginx as reverse proxy. Deploy Django with Gunicorn behind Nginx. Configure SSL for both. Set up process managers (Supervisor or systemd) for both PHP-FPM and Gunicorn. Monitor error logs for 2 weeks. Declare Phase 1 complete.

🧪 Testing Strategy During Migration

  • Run PHP and Django in parallel — compare outputs from both for the same data before switching
  • Feature flags — add a config toggle in PHP that switches between old PHP logic and new Django API calls
  • Database snapshots — take a DB backup before each phase in case rollback is needed
  • Postman/Insomnia — test every Django endpoint manually before connecting to PHP
  • PHP error logging — log all cURL responses to a file during testing to catch silent failures

Setup Instructions

Prerequisites

  • PHP 8.x + Apache or Nginx
  • Python 3.11+ installed
  • MySQL 8 or PostgreSQL 15
  • pip (Python package manager)
  • Git for version control
  • Composer (optional, for PHP deps)

Required Python Packages

  • django — core framework
  • djangorestframework — REST API (DRF)
  • djangorestframework-simplejwt — JWT auth
  • django-cors-headers — CORS for PHP calls
  • mysqlclient or psycopg2 — DB driver
  • python-dotenv — .env file loading
Django Setup Commands BASH 
  # 1. Navigate to your projects folder
  cd /var/www/

  # 2. Create Django project
  django-admin startproject spacio_api
  cd spacio_api

  # 3. Create virtual environment
  python -m venv venv
  source venv/bin/activate          # Linux/Mac
  venv\Scripts\activate             # Windows

  # 4. Install dependencies
  pip install django djangorestframework djangorestframework-simplejwt
  pip install django-cors-headers python-dotenv mysqlclient

  # 5. Save dependencies
  pip freeze > requirements.txt

  # 6. Create Django apps
  python manage.py startapp authentication
  python manage.py startapp reservations
  python manage.py startapp availability
  python manage.py startapp reports
  python manage.py startapp issues

  # 7. Copy your .env file and fill in YOUR_ placeholders
  cp .env.example .env
  nano .env

  # 8. Run migrations (Django-managed tables only)
  python manage.py migrate

  # 9. Start Django development server
  python manage.py runserver 0.0.0.0:YOUR_DJANGO_PORT
Running Both Servers Locally BASH 
  # Terminal 1 — Start PHP (Apache)
  # If using XAMPP/WAMP: start via control panel
  # If using built-in PHP server:
  cd /var/www/spacio
  php -S localhost:YOUR_PHP_PORT

  # Terminal 2 — Start Django
  cd /var/www/spacio_api
  source venv/bin/activate
  python manage.py runserver 0.0.0.0:YOUR_DJANGO_PORT

  # Verify both are running:
  # PHP:    http://localhost:YOUR_PHP_PORT
  # Django: http://localhost:YOUR_DJANGO_PORT/api/v1/
  # Admin:  http://localhost:YOUR_DJANGO_PORT/admin/
Nginx Config — Route PHP + Django NGINX 
  # /etc/nginx/sites-available/spacio.conf

  server {
      listen 80;
      server_name YOUR_ALLOWED_HOSTS;

      # Route /api/* to Django (Gunicorn)
      location /api/ {
          proxy_pass http://127.0.0.1:YOUR_DJANGO_PORT;
          proxy_set_header Host $host;
          proxy_set_header X-Real-IP $remote_addr;
          proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      }

      # Route everything else to PHP
      location / {
          root YOUR_PHP_PROJECT_PATH;
          index index.php;

          location ~ \.php$ {
              fastcgi_pass unix:/var/run/php/php8.2-fpm.sock;
              fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
              include fastcgi_params;
          }
      }
  }
✓
Local Development Tip: You don't need Nginx locally. Run PHP on :8080 and Django on :8000. In your PHP .env, set DJANGO_API_URL=http://localhost:8000. Everything works without Nginx during development.
